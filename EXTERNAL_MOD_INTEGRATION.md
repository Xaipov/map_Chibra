# Внешняя интеграция мода Minecraft

Этот документ описывает рекомендуемый сценарий, в котором мод Minecraft
передаёт на карту сведения о самосборе (`can_create_block`).

## Рекомендуемый пользовательский сценарий

1. Мод отслеживает игрока и периодически обновляет данные только по блокам,
   находящимся рядом с ним. Не нужно сканировать весь мир или всю карту.
2. Возможные точки самосбора показываются игроку фиолетовыми партиклами.
   Партиклы являются только визуальной подсказкой и не изменяют данные карты.
3. Когда мод обнаруживает фиолетовые партиклы, он спрашивает игрока:
   **«Здесь есть самосбор?»**
4. Только после ответа игрока мод отправляет результат на сервер:
   - `true` — самосбор подтверждён;
   - `false` — самосбора нет.
5. Сервер сохраняет результат как временный статус. Карта получает его через
   Supabase Realtime и окрашивает подтверждённый самосбор в фиолетовый цвет.

Если игрок не ответил, мод не должен отправлять значение `false`: отсутствие
ответа означает, что проверка не завершена.

## Обновление данных рядом с игроком

Рекомендуемые параметры:

- радиус проверки задаётся конфигурацией мода;
- проверять нужно только блоки в текущем радиусе игрока;
- повторную отправку для одного блока следует ограничивать cooldown-ом;
- после выхода игрока из области блок можно перестать обновлять;
- перед отправкой нужно убедиться, что блок сопоставлен с корректным `block_id`
  карты.

Пример алгоритма:

```text
при перемещении игрока или таймере:
  nearby_blocks = найти блоки в радиусе игрока

  для каждого блока:
    если обнаружены фиолетовые партиклы:
      спросить игрока «Здесь есть самосбор?»

      если ответ «Да»:
        отправить update_can_create_from_mod(block_id, true, 1)
      если ответ «Нет»:
        отправить update_can_create_from_mod(block_id, false, 1)
      если ответа нет:
        ничего не отправлять
```

## Отправка подтверждения на сервер

Вызов выполняется только с доверенного серверного кода мода, прокси или Edge
Function. `service_role` ключ нельзя помещать в клиентский мод или раздавать
игрокам.

```http
POST https://<PROJECT_REF>.supabase.co/rest/v1/rpc/update_can_create_from_mod
Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>
apikey: <SUPABASE_SERVICE_ROLE_KEY>
Content-Type: application/json

{
  "p_block_id": 42,
  "p_can_create": true,
  "p_expires_hours": 1
}
```

Для ответа «Нет» используется такой же запрос с
`"p_can_create": false`. Время `p_expires_hours` должно быть больше нуля,
чтобы статус считался временным и автоматически устаревал. Значение `1`
соответствует стандартному сроку в один час.

Подробное описание RPC, Edge Function и альтернативного PATCH-сценария
находится в [MOD_INTEGRATION.md](./MOD_INTEGRATION.md).

## Ключ уведомлений для администратора

Администратор карты может создать ключ в панели **«Уведомления о самосборе»**.
Ключ показывается только один раз — сохраните его в защищённом хранилище мода.
В базе хранится только SHA-256 хеш ключа, поэтому восстановить его через карту
нельзя. При утечке ключа администратор должен отозвать его в Supabase и создать
новый (интерфейс отзыва будет добавлен отдельно).

Внешний мод передаёт уведомление через RPC:

```http
POST https://<PROJECT_REF>.supabase.co/rest/v1/rpc/receive_self_assembly_notification
Authorization: Bearer <SUPABASE_ANON_OR_SERVICE_ROLE_KEY>
apikey: <SUPABASE_ANON_OR_SERVICE_ROLE_KEY>
Content-Type: application/json

{
  "p_key": "sam_<generated-key>",
  "p_block_id": 42,
  "p_can_create": true,
  "p_message": "Фиолетовые партиклы подтверждены",
  "p_observed_at": "2026-09-15T02:00:00.000Z"
}
```

RPC возвращает идентификатор уведомления. После вставки запись появляется в
`self_assembly_notifications` через Supabase Realtime. Для отправки с клиента
мода используйте только отдельный защищённый ключ Supabase; `service_role`
нельзя помещать в мод, распространяемый игрокам.

## Надёжность и безопасность

- Не доверяйте одному факту появления партиклов: всегда спрашивайте игрока.
- Не отправляйте запрос без ответа игрока.
- Валидируйте `block_id`, координаты и срок действия на сервере.
- Ограничьте частоту запросов от одного игрока и одного блока.
- Повторная отправка должна быть идемпотентной: новый результат заменяет
  предыдущий временный статус.
- Логи мода не должны содержать `service_role` ключ.

## Отображение на карте

Для активного статуса `true` карта использует фиолетовую окраску блока.
Временный статус дополнительно отображается как временный в карточке блока.
После истечения срока карта помечает данные как устаревшие, поэтому мод должен
обновлять блок при следующем обнаружении рядом с игроком.
